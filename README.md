# Editing site

Онлайн-редактор видео на VM с API для внешнего агента. Дизайн: `docs/superpowers/specs/2026-09-03-video-editor-design.md`.

## Локальный запуск

```bash
uv sync
cp .env.example .env            # заполнить VIDEO_ADMIN_EMAIL и ключи Yandex
uv run uvicorn server.app.main:app --reload --port 8010
cd web && npm install && npm run dev   # интерфейс на http://localhost:5173, /api проксируется на 8010
```

## Тесты

```bash
uv run python -m pytest
uv run ruff check .
cd web && npm test
```

## Загрузка и файлы (M1a)

- `POST /api/v1/uploads` → `PUT /api/v1/uploads/{id}/chunks/{n}` (сырые байты, 32 МиБ) → `GET /api/v1/uploads/{id}` (докачка) → `POST /api/v1/uploads/{id}/complete` → `asset_id`. Справочный клиент: `python tools/upload_file.py https://video.cloudrudesign.ru $TOKEN clip.mp4`.
- Мелкие файлы (SRT, музыка до 64 МиБ): `POST /api/v1/assets/upload` (multipart `file`, необязательно `kind`).
- `GET /api/v1/assets`, `GET /api/v1/assets/{id}` (ссылки на `proxy`, `thumbs`, `peaks`, `analysis` появляются по статусу), `DELETE /api/v1/assets/{id}`. Квота и использование в `GET /api/v1/me`.
- Файлы: `/files/{user_id}/assets/{asset_id}/<имя>`; на VM отдаёт Caddy после `forward_auth` в `/internal/authz`, локально само приложение. `source.*` наружу не отдаётся.
- Пределы: 5 ГБ на файл, 20 ГБ на человека, 20 новых загрузок в час, отказ при свободном диске меньше 10 %.
- Janitor (`python -m server.janitor`, таймер раз в час): загрузки старше 24 ч, ассеты без обращений старше 24 ч, сироты на диске старше часа, зависшие задания, просроченные сессии, суточный бэкап базы в `data/backups/` (7 копий).
- Локальный запуск: `VIDEO_TMP_DIR` по умолчанию `data/tmp`; на VM `/srv/video/tmp` (тот же раздел, что `/srv/video/data`).
### Обработка (M1b)

- Воркер `video-worker` (`python -m server.worker`) берёт задания из таблицы `jobs`, одно за раз, полоса `cpu`. Пульс раз в 10 с виден в `/healthz` полем `worker_seen_sec_ago`; пульс старше 2 минут переводит здоровье в `degraded`. Логи: `journalctl -u video-worker`.
- `analyze` (приоритет 10): `ffprobe` даёт длительность, размеры, частоту кадров и кодеки; звук уходит в WAV 16 кГц, из него считаются пики (`peaks.json`, 50 значений в секунду) и две карты пауз (`analysis.json`); для видео собирается полоска кадров (`thumbs.jpg` и раскладка `thumbs.json`). Ассет переходит в `ready`.
- `proxy` (приоритет 5): H.264 до 640 px по длинной стороне, CRF 28, ключевой кадр каждые 30 кадров, звук AAC 96 кбит; для звуковых ассетов `proxy.m4a`. Кадр меньше 640 px не увеличивается. Ассет переходит в `proxy_ready`.
- Порог тишины не абсолютный: уровень речи (медиана самых громких 2 % окон) минус 16 дБ, не ниже −60 дБ. Если пауз не нашлось, порог опускается ещё на 10 дБ.
- Отмена и остановка: удаление ассета отменяет его задания, воркер видит это при следующем пульсе и останавливает ffmpeg. При перезапуске сервиса незавершённое задание возвращается в очередь, а не теряется до прихода janitor.
- Временный файл прокси пишется с суффиксом `.part`, поэтому формат контейнера задаётся явно (`-f mp4`, `-f ipod`): по такому имени ffmpeg его не угадывает.

### Проекты (M2a)

- `POST /api/v1/projects` `{name, doc?}` создаёт проект, `GET /api/v1/projects` отдаёт список без документов, `GET /api/v1/projects/{id}` — проект целиком.
- `PUT /api/v1/projects/{id}` `{name, version, doc}` сохраняет документ целиком. Версия должна совпадать с текущей, иначе `409 version_conflict` и актуальный проект в `details.project`.
- `DELETE /api/v1/projects/{id}` удаляет проект. `POST /api/v1/projects/{id}/finish` завершает его: проект остаётся историей, а его файлы удаляются, если не заняты другими незавершёнными проектами.
- Документ: `output` (`aspect` 16:9 / 9:16 / 1:1, `fit` pad / crop, `fps` 25 / 30 / 50 / 60), `clips` (до 100, каждый — ассет плюс `in` и `out`), `music`, `subtitles`. Ошибки проверки приходят списком: `422 invalid_project`, в `details.errors` пары «поле, сообщение». Неизвестные поля отбрасываются, флаги подтверждения выставляет только сервер.
- Клип с `snap_to_pauses: true` сервер подтягивает к измеренной паузе: окно ±0.35 с, отступ 0.3 с внутрь паузы, не дальше её середины. Получилось — `in_verified` / `out_verified` становятся `true`; паузы рядом нет — время остаётся, флаг `false`. Рез внутри непрерывной речи молча не делается.
- Файл, занятый в незавершённом проекте, не удаляется: `409 asset_in_use` со списком проектов.
- Загруженные субтитры конвертируются в WebVTT рядом с исходником (`subs.vtt`), ссылка приходит в карточке файла.

### Редактор в браузере (M2b)

- Экраны разводит хеш: `#/` — файлы, проекты и настройки, `#/p/{id}` — редактор проекта.
- Слева панель исходника: выбрать готовое видео, проиграть прокси, отметить начало и конец, положить кусок на шкалу.
- Шкала: блоки клипов с кадрами из полоски и звуковой волной, перетаскивание меняет порядок, ручки по краям подрезают, кнопка режет клип по курсору, выбранный клип удаляется. Неподтверждённая граница помечена восклицательным знаком.
- Плеер играет склейку целиком: два элемента `video` меняются местами на стыке, следующий клип подгружается заранее. Кадр показывается в пропорции вывода.
- Правки уезжают на сервер через 500 мс тишины, по одному запросу за раз, и следующая правка отправляется уже с версией из ответа. Ответ сервера заменяет документ: в нём подтянутые резы и новая версия. Если проект изменили в другом месте, редактор показывает свежую версию и говорит об этом.

### Точки сохранения и навигация (M2c)

- Кнопка «Сохранить точку» снимает состояние проекта. Пул хранит пять последних точек, старые вытесняются. Кнопка «Вернуться» кладёт снимок обратно как обычное сохранение, поэтому версия растёт и откатить откат тоже можно.
- API: `POST /api/v1/projects/{id}/checkpoint` `{label?}`, `GET /api/v1/projects/{id}/versions`, `POST /api/v1/projects/{id}/restore` `{version_id}`. Размер пула задаёт `VIDEO_VERSIONS_KEPT`.
- Автосохранение в пул не пишет: оно срабатывает каждые полсекунды тишины и вытеснило бы всё осмысленное.
- Навигация по шкале: клик ставит курсор, полоса под линейкой и сама линейка перематывают перетаскиванием, пробел играет и останавливает, стрелки двигают курсор на секунду (с Shift на 0.1 с), Home и End прыгают на края. Текущее время видно рядом с общим, курсор сам подтягивает прокрутку.

### Таймкоды, индикация переноса и отмена (M2d)

- В панели исходника под плеером идёт полоса всего файла: выделенный кусок залит, границы тянутся ручками, риска показывает текущий кадр. Начало и конец задаются и полем таймкода: `83.5`, `1:23.5`, `1:02:03.4`; запятая вместо точки тоже принимается. Непонятный ввод подсвечивается и границу не двигает.
- В редакторе текущее время — поле ввода: наберите таймкод и нажмите Enter, курсор прыгнет туда.
- При переносе клипа пунктирный призрак показывает, куда он встанет, а подпись называет номер будущей позиции. Призрак считается той же функцией, что выполняет перенос, поэтому показ не расходится с результатом.
- Кнопка «Отменить» и Ctrl+Z откатывают последнее действие, в памяти пять последних состояний. История живёт в странице и не переживает перезагрузку: для долгого хранения есть точки сохранения. При конфликте версий история чистится, потому что база сменилась под нами.

- Известное ограничение: завершение загрузки не идемпотентно. Если ответ на `complete` потерялся в сети уже после успеха на сервере, запись о загрузке удалена, и следующая попытка создаст вторую загрузку того же файла, то есть дубль ассета и лишний расход квоты. Дубль виден в списке и удаляется вручную.

### Рендер (M3)

- `POST /api/v1/projects/{id}/render` `{quality: "draft" | "final"}` → `202` и `job_id`. Ход виден в `GET /api/v1/jobs/{job_id}` (`progress` от 0 до 1), отмена — `POST /api/v1/jobs/{job_id}/cancel`.
- `GET /api/v1/projects/{id}/renders` — готовые ролики со ссылкой `download`; `GET|DELETE /api/v1/renders/{id}` — карточка и удаление.
- Черновик: короткая сторона 720, пресет `ultrafast`, CRF 26, звук 128 кбит. Финал: 1080, `veryfast`, CRF 20, 160 кбит. Разрешение выводится из пропорции проекта.
- Готовый файл живёт сутки и скачивается по `/files/{user}/projects/{project}/renders/{id}.mp4` с `Content-Disposition: attachment`.
- Один выполняющийся рендер и два в очереди на человека. Перед запуском воркер проверяет, что файлы на месте и не ниже `ready`, а на диске есть место под результат.
- Завершение проекта удаляет его рендеры вместе с файлами.
- В редакторе панель «Сборка»: две кнопки, полоса прогресса с отменой и список готовых роликов со скачиванием.
- Сквозной прогон сценария агента: `python tools/agent_smoke.py https://video.cloudrudesign.ru $TOKEN clip.mp4`.

### Транскрипция (M4a)

- `POST /api/v1/assets/{id}/transcribe` `{language?}` → `202` и `{job_id, language}`; ход задания виден в `GET /api/v1/jobs/{job_id}`. Язык по умолчанию — `VIDEO_TRANSCRIBE_LANGUAGE`, провайдеру он уходит всегда: без него маршрут отвечает `400`. Отказы: `422 asset_not_ready` (анализ не закончен, карты пауз ещё нет), `422 no_audio`, `409 transcript_exists`, `409 already_queued`, `503 transcription_unavailable`.
- `GET /api/v1/assets/{id}/transcript?format=json|srt|vtt` — транскрипт во времени исходника, SRT и VTT собираются из JSON на лету; транскрипта нет — `404`. `PUT` того же адреса принимает свой транскрипт `{segments: [{start, end, text, words?}], language?}` (`422 invalid_transcript` на пустом тексте или `end` не больше `start`). `DELETE` убирает и строку в базе, и `transcript.json`. Пока задание в очереди или выполняется, `PUT` отвечает `409 already_queued`: иначе доехавший воркер молча затёр бы чужой файл. Ссылка на ручку приходит в карточке файла полем `files.transcript`.
- Задание идёт в полосе `net`, а рендеры — в `cpu`: воркер держит обе полосы своими потоками, у каждого своё соединение с базой. Транскрипция ждёт сеть десятками минут и очередь сборок за собой не держит.
- Звук режется на чанки с целью в 10 минут: в пределах ±60 с от цели ищется пауза, рез ставится по её середине, хвост короче четверти цели остаётся у предыдущего чанка. Кусок — MP3 64 кбит / 16 кГц / моно (нет `libmp3lame` в сборке ffmpeg — WAV), уходят по четыре сразу; на `413` кусок делится пополам и обе половины отправляются заново. Один нерасшифрованный кусок валит задание целиком: по тексту с дырой в середине всё равно будут монтировать, не зная о дыре.
- **Провайдер не отдаёт пословных таймкодов.** Слова размечаем сами: длительность сегмента делится между словами пропорционально слогам и раскладывается только по звучащим интервалам, каждое слово помечено `interpolated`. Точность такой раскладки около ±0.3 с, **резать по этим границам нельзя** — для резов есть `snap_to_pauses` по измеренным паузам.
- Границы сегментов сверяются с плотной картой тишин: расширить речь разрешено до секунды, сжать — до четверти; сегменты при этом не переставляются, не наезжают друг на друга и не становятся короче 0.05 с. Края речи рядом нет — граница остаётся на месте с флагом `false`: «проверить нечем» честнее, чем двигать вслепую. В `stats` доля подтверждённых границ (`verified_pct`), число сдвинутых сегментов (`adjusted`) и наибольший сдвиг (`max_drift`).
- На шве чанков фраза приходит дважды — хвостом одного куска и головой следующего: голову подрезаем к концу хвоста, а остаток короче 0.3 с выбрасываем, это обрывок того же дубля. Времена клэмпятся к длительности ассета: Whisper регулярно тянет последний сегмент за конец аудио (в живом прогоне окно 600–780 кончилось на 783.9), и такой субтитр висел бы там, где кадров уже нет.
- Пустой `VIDEO_TRANSCRIBE_API_KEY` выключает функцию: ручка отвечает `503`, а не уходит в сеть без авторизации, потратив нарезку и трафик. Воркер проверяет то же и в том же порядке.
- Загруженный свой транскрипт не верифицируется: времена в нём настоящие, двигать их нечем и незачем. Слова переносятся как есть, без пометки `interpolated`, — по ним резать можно. Остаются проверка формата и клэмп к длительности ассета.
- В JSON рядом с сегментами лежат обе карты пауз (`silences`, `silences_dense`): текст и паузы приезжают одним запросом. Сегменты с сомнительными метриками провайдера помечены `suspect`, но не выброшены — что делать с такой репликой, решает человек.
- Сквозной прогон заказывает расшифровку и печатает долю подтверждённых границ; там, где ключ не настроен, шаг говорит об этом и пропускается, а прогон идёт дальше.

## Разработка интерфейса

Два способа увидеть интерфейс локально:

- **Сборка + один сервер.** `cd web && npm run build`, затем `uv run uvicorn server.app.main:app --port 8010`: приложение раздаёт `web/dist` на `/`, cookie и проверка Origin работают как на VM.
- **Vite dev-сервер** (`cd web && npm run dev`, страница на http://localhost:5173, `/api` проксируется на 8010). Проверка cross-site сравнивает `Origin` с `VIDEO_PUBLIC_BASE_URL`, поэтому на время разработки в `.env` ставь `VIDEO_PUBLIC_BASE_URL=http://localhost:5173` (redirect URI приложения Яндекса должен совпадать).

### Субтитры из транскрипта и панель (M4b)

- `doc.subtitles` с `source: "transcript"` собирает субтитры сам: слова расшифровки пересчитываются через клипы проекта в шкалу готового ролика (слово с временем `t` внутри клипа `k` получает `offset_k + (t − in_k)`, слова на стыках обрезаются). Брать слова исходника как есть нельзя — в ролике остались только выбранные куски и в другом порядке.
- Реплики режутся по типографским правилам (спека §10.9): не кончаются предлогом, союзом, голым числом или открывающей кавычкой; точка и запятая на конце снимаются, вопросительный и восклицательный остаются; строки уравновешены, при равном балансе верхняя короче. Ширина строки зависит от кадра — 42 знака для 16:9, 24 для 9:16, 32 для 1:1.
- Кэш `subs/{version}.srt` и `.vtt` в каталоге проекта. Пересобирается при новой версии документа и когда расшифровка новее кэша: версия следит за документом, но не за расшифровкой.
- `GET /api/v1/projects/{id}/subtitles?format=srt|vtt` отдаёт готовый файл; `422 no_transcript_subtitles` — у документа не заданы субтитры из расшифровки, `422 no_transcript` — у файла нет расшифровки.
- Режимы `burn` и `soft` работают одинаково для обоих источников: разница только в том, откуда взялся файл.
- В редакторе под панелью исходника — панель транскрипта: клик по слову перематывает плеер, протаскивание выделяет фразу, «Взять кусок» кладёт её на шкалу клипом со снэпом к паузам. Подозрительные реплики и неподтверждённые границы помечены тихо: полоской и подсказкой, а не пестротой.

## Единый кабинет администрирования

- Страница в админке: одна таблица, строка — человек, столбцы — три сервиса ВМ (Видео, Доска, Трансляции). Галочка даёт или снимает доступ к одному сервису, форма заводит человека сразу в несколько.
- `GET /api/v1/admin/cabinet` — состояние сервисов и таблица допуска; `POST /api/v1/admin/cabinet/access` `{email, grant[], revoke[]}` — правки. Ответ всегда `200`, результат по каждому сервису лежит в теле: три сервиса — три независимые операции, а не транзакция, и удавшееся не откатывается.
- К соседям ходит сервер по loopback с заголовком `X-Service-Token`, браузер к ним не обращается. Секреты — `STREAM_SERVICE_TOKEN` и `BOARD_SERVICE_TOKEN` в `.env`, **без префикса** `VIDEO_` (у соседей та же переменная своя). Пустой секрет запрещает доступ: сервис помечен «не настроен», кнопки к нему выключены.
- Недоступный сосед забирает только свой столбец: в нём «не знаем», а не «нет доступа». Отказ в служебном токене показывается иначе, чем молчание сервиса.
- Доступ администратора кабинетом не меняется — он задан конфигурацией каждого сервиса, и в его строке стоит подпись, а не галочки. Попытка снять через API даёт `422 cannot_change_admin`.
- Снятие доступа обрывает сессии сразу, и подтверждение об этом предупреждает.
- Свои админки у сервисов остаются: если Editing site лежит, доступ к остальным двум должен оставаться управляемым.

## Деплой

1. DNS: A-запись поддомена на VM. Приложение Yandex OAuth с redirect URI `https://<домен>/api/v1/auth/callback` и правами `login:email login:info`.
2. Приватный репозиторий: положить deploy key в `/etc/editing-site/deploy_key` (bootstrap выставит права), публичный HTTPS-URL ключа не требует.
3. Один раз на чистой Ubuntu 24.04: `sudo bash bootstrap.sh <домен> <git-url>`, затем заполнить `/opt/editing-site/.env` (`VIDEO_DATA_DIR=/srv/video/data`, `VIDEO_PUBLIC_BASE_URL=https://<домен>`, `VIDEO_COOKIE_SECURE=true`, ключи Yandex, `VIDEO_ADMIN_EMAIL`).
4. Каждый релиз: `sudo bash /opt/editing-site/deploy/deploy.sh` (fast-forward `main`, зависимости, сборка интерфейса, миграции, переустановка Caddyfile и юнита, рестарт, ожидание `status=ok` в `/healthz`).
5. Замер скорости ffmpeg на машине: `sudo -u video .venv/bin/python tools/bench_ffmpeg.py --out /tmp/bench-report --work /srv/video/tmp/bench` из `/opt/editing-site`, отчёт скопировать в `docs/benchmarks/` локально.

`/healthz` отвечает 503 при статусе degraded (диск меньше 10 %, база недоступна, пульс воркера старше 120 с), так что внешний пинг по коду ответа достаточен.

## Соседи на той же VM

VM общая с сервисом VideoBoard (`/opt/videoboard`, пользователь `board`, порт 8020). Договорённости:

- `/etc/caddy/Caddyfile` наш и переписывается `deploy.sh` целиком; чужие site-блоки живут в `/etc/caddy/conf.d/*.caddy` и подключаются строкой `import` в начале нашего Caddyfile. Сосед валидирует общий конфиг перед каждым `systemctl reload caddy`.
- Yandex OAuth-приложение общее: у него два redirect URI, а `client_id`/`client_secret` лежат в обоих `.env`. Ротация секрета кладёт оба сервиса, перед сменой предупредить чат VideoBoard.
- Диск общий: у нас файлы живут сутки и квота 20 ГБ на человека, у соседа потолок 30 ГБ и TTL 30 дней; порог отказа в загрузке у обоих 10 % свободного места.
- Модули `server/app/auth/*`, `server/db/*`, `config`, `errors`, `ratelimit`, `security` скопированы к соседу как основа; найденные в них баги сообщать в чат VideoBoard.
