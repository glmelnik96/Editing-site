# Единый кабинет администрирования трёх сервисов — дизайн

**Дата:** 2026-09-05
**Репозиторий:** Editing site (кабинет живёт здесь)
**Затрагивает:** VideoBoard, Presentation Remote — задачи им лежат у них в `docs/`

---

## 1. Зачем

На ВМ `176.109.109.251` живут три самостоятельных сервиса с одинаковой моделью
входа — Яндекс OAuth плюс белый список допущенных адресов:

| Сервис | Домен | Порт |
|---|---|---|
| Editing site | `video.cloudrudesign.ru` | 8010 |
| VideoBoard | `board.cloudrudesign.ru` | 8020 |
| Presentation Remote | `stream.cloudrudesign.ru` | 8014 |

Чтобы завести человека, приходится обойти три админки на трёх доменах и трижды
вспомнить, где какая кнопка. Кабинет собирает это в одно место.

**Чего кабинет не делает:** не централизует хранилище. Каждый сервис остаётся
хозяином своего списка — см. §3.

---

## 2. Принятые решения

| Вопрос | Решение |
|---|---|
| Где живёт | В Editing site, страницей в его админке |
| Архитектура | Агрегатор: данные у сервисов, кабинет ходит к ним |
| Сколько списков | Три, по одному на сервис, но ведутся из одного места |
| Что значит «допущен» | Всё, кроме администрирования; под-прав внутри сервиса нет |
| Кто администратор | Один человек, `g.melnikov96@yandex.ru`, задан конфигом каждого сервиса |
| Права администратора | Кабинетом не выдаются и не отзываются — это константа |

**Почему три списка, а не один.** Общий список означал бы, что подрядчик-
монтажёр, допущенный к видеоредактору, автоматически получает доступ к
презентациям. При трёх списках «дать всё» — одно нажатие на три галочки, а вот
«дать только видеоредактор» при одном списке невозможно вовсе.

**Почему агрегатор, а не общая база.** Один файл SQLite на три процесса — это
блокировки (у соседей голый `sqlite3`, у Presentation Remote SQLAlchemy), и он
разваливается, как только сервис уезжает на другую машину. Presentation Remote
переезжал 2026-09-05 — аргумент не теоретический.

---

## 3. Архитектура

```
браузер ──► video.cloudrudesign.ru/admin   (кабинет — эта страница)
                    │
     наш сервер ────┼── свой список          → прямым вызовом функций
                    ├── board  /api/v1/admin/whitelist  ─┐ HTTP со служебным
                    └── stream /api/admin/allowed        ─┘ токеном, loopback
```

К соседям ходит **сервер** Editing site, а не браузер. Отсюда два следствия:
CORS не нужен вовсе, а служебные токены не покидают сервер.

Ходим по `127.0.0.1:8020` и `127.0.0.1:8014` напрямую, минуя Caddy и интернет:
все три сервиса на одной машине.

Свой список кабинет правит прямым вызовом. HTTP-запрос к самому себе означал бы
второй способ делать то же самое и второе место, где можно ошибиться.

### Что уже есть и совпадает

Интерфейсы соседей писать не нужно — они существуют и почти одинаковы:

```
VideoBoard            GET|POST /api/v1/admin/whitelist   DELETE /api/v1/admin/whitelist/{email}
Presentation Remote   GET|POST /api/admin/allowed        DELETE /api/admin/allowed/{email}
```

Различаются пути и форма ответа. Это нормализует адаптер на нашей стороне (§5),
а не переделка чужих сервисов.

## 4. Служебный доступ — единственное, что меняется у соседей

Сейчас правки белого списка у нас и у VideoBoard закрыты `require_admin_cookie`
с комментарием: «Правки whitelist только из браузера: токен агента не должен
заводить новых людей». Решение верное, отменять его нельзя.

Кабинет — машинный клиент и под это условие не подходит. Нужен **третий вид
доступа**, узкий и отдельный:

- заголовок `X-Service-Token`, сверка через `hmac.compare_digest`;
- действует **только** на маршрутах белого списка, больше нигде;
- не даёт ни сессии, ни роли: это право выполнить конкретную операцию, а не
  «вход от имени администратора»;
- секрет свой у каждого сервиса, лежит в его `.env`; у кабинета — два чужих
  секрета в своём;
- **пустой или незаданный секрет запрещает доступ, а не разрешает.** Иначе
  забытая переменная открывает список наружу.

Токен агента (`/api/v1/tokens`) для этого не годится: он выдаётся людям, и его
компрометация не должна давать управление допуском.

## 5. Адаптер сервисов

Каждый сервис описывается одной структурой; кабинет не знает про их различия.

```python
@dataclass(frozen=True)
class RemoteService:
    key: str            # "board" | "stream"
    title: str          # как показывать
    base_url: str       # http://127.0.0.1:8020
    list_path: str      # /api/v1/admin/whitelist
    item_path: str      # /api/v1/admin/whitelist/{email}
    token_env: str      # имя переменной с секретом
```

Адаптер приводит ответы к общему виду `{email, note, added_by}`: у соседей поля
называются по-разному, и тащить эти различия в UI незачем.

Свой сервис описан такой же структурой, но с локальной реализацией — единый
интерфейс, две реализации (HTTP и прямой вызов).

## 6. Что показывает кабинет

Одна таблица: строка — человек, столбцы — сервисы.

```
адрес                        Видео   Доска   Трансляции
liza.orlesss01@yandex.ru       ✓       —          ✓
g.m.cloud@yandex.ru            ✓       ✓          ✓
```

- **Добавить** — поле адреса и три галочки: куда пускаем.
- **Изменить** — щелчок по галочке даёт или снимает доступ к одному сервису.
- **Убрать отовсюду** — отдельное действие с подтверждением.
- Администратор в таблице виден, но его галочки заблокированы: доступ у него из
  конфига, снять его кабинетом нельзя — иначе можно запереть себя.

**Снятие доступа обрывает сессии.** У Presentation Remote это явный отзыв, у нас
и у VideoBoard — через флаг `disabled`, который `resolve_session` проверяет на
каждом запросе. Результат одинаковый, и подтверждение обязано об этом
предупреждать: человека выкинет сразу, а не «когда-нибудь».

## 7. Отказы

Кабинет говорит с двумя чужими сервисами по сети, и они бывают недоступны.

| Случай | Поведение |
|---|---|
| Сосед не ответил на чтение | Его столбец: «недоступен». Остальные работают |
| Сосед не ответил на запись | Явная ошибка с именем сервиса; состояние **не** притворяется применённым |
| Запись прошла у одного из трёх | Показываем поимённо, что удалось, а что нет |
| Служебный токен не принят | «Сервис отказал в доступе» — это не то же, что «недоступен» |
| Секрет не задан в конфиге | Сервис помечен «не настроен», кнопки к нему выключены |

Кабинет **не откатывает** частично применённые изменения: три сервиса — это три
независимые операции, а не транзакция, и притворяться иначе значит врать. Вместо
этого показываем результат по каждому и даём повторить.

---

## 8. Что остаётся у сервисов

Собственные админки **никуда не деваются**. Причина простая: если Editing site
лежит, доступ к остальным двум должен оставаться управляемым. Кабинет —
удобство, а не единственный путь.

---

## 9. Тестирование

**Адаптер** — на подменённом HTTP-клиенте, без сети: чтение, добавление,
удаление, нормализация полей, поведение при 401, 500 и таймауте.

**Кабинет** — три источника собираются в одну таблицу; недоступный сосед не
ломает остальные столбцы; частичный успех показан поимённо; галочки
администратора заблокированы.

**Служебный токен** (в каждом из трёх сервисов) — принимается на маршрутах
списка; **не** принимается больше нигде; неверный даёт 403; незаданный секрет
запрещает, а не разрешает; сравнение не зависит от времени.

**Живая проверка** после выкатки — браузером, а не curl: завести адрес во все
три, убедиться, что человек входит во все три; снять в одном — проверить, что
там выкинуло, а в остальных доступ остался.

---

## 10. Вне рамок

- Общее хранилище личностей и единый вход (SSO) — другая задача.
- Роли внутри сервисов: их нет по решению §2.
- Статистика и содержимое сервисов: кабинет про допуск, а не про данные.
- Отдельный журнал аудита: у каждого сервиса уже пишется `added_by`.

## 11. Что требуется от соседей

По одной задаче каждому, описания лежат у них в репозиториях:

- **Presentation Remote** — `docs/TASK-from-unified-admin.md`: служебный токен
  плюс отказ от `can_create_rooms` (допущен ⇒ может вести).
- **VideoBoard** — `docs/TASK-from-unified-admin.md`: только служебный токен.

Оба изменения обратно совместимы: браузерная админка каждого сервиса продолжает
работать как раньше.
