# Editing site: онлайн-редактор видео на VM с API для агента

**Дата:** 2026-09-03
**Статус:** дизайн согласован в брейншторме, ждёт вычитки
**Папка проекта:** `C:\Users\Глеб\Documents\Editing site`

## 1. Цель и рамки

Простой онлайн-редактор для небольшой команды: загрузил записи, собрал ролик из кусков на одной дорожке, наложил музыку и субтитры, отрендерил в нужном формате, скачал. Вся обработка идёт на отдельной VM в Cloud.ru Evolution. HTTP API является первоклассным продуктом с первого дня: браузерный интерфейс лишь один из его клиентов, вторым станет внешний ИИ-агент, который живёт не на VM и монтирует по транскрипту.

### Решения брейншторма

| Вопрос | Решение |
|---|---|
| Где обработка | На VM, серверно. Гибрид с браузерным превью возможен позже, формат проекта и API к этому готовы |
| Где живёт сервис | Отдельная новая VM, не под шлюзом платформы cloudrudesign.ru |
| Что умеет первая версия | Склейка на одной дорожке: клипы с точками входа и выхода, порядок, музыка, субтитры, экспорт в 16:9, 9:16, 1:1 |
| Пользователи | Небольшая команда по whitelist, вход через Yandex OAuth, у каждого свои проекты и квота |
| Материал | Файлы до 5 ГБ, бывают часовые записи. Диск временный: после проекта очистка, срок жизни ассета и рендера 1 день |
| Агент | Внешний, работает через API с токеном. Основная роль: монтажёр по транскрипту |
| Транскрипция | Через внешний API провайдера, на VM ничего не считаем |
| Подход к сборке | Своё приложение: FastAPI + SQLite + воркер + ffmpeg, фронтенд на TypeScript, всё за Caddy как systemd-сервисы |
| VM | Слабая, уровня машины App1..App3. Без GPU |

### Не делаем в первой версии

- Мультитрек, наложения, картинка в картинке, текст поверх видео, ключевые кадры.
- Переходы кроме склейки встык. Скорость воспроизведения клипа.
- Публичную регистрацию, платёжку, роли сложнее «администратор / пользователь».
- Совместное редактирование одного проекта в реальном времени.
- Запуск Whisper на VM. Пословный forced alignment.
- Сырые аргументы ffmpeg от клиента.

## 2. Архитектура

```
Браузер (SPA)  ──cookie──┐
                         ├──▶ Caddy (TLS) ──▶ FastAPI «video-api» ──▶ SQLite
Агент (внешний) ─Bearer──┘        │                 │
                                  │ forward_auth     │ таблица jobs
                                  ▼                  ▼
                            file_server        «video-worker» ──▶ ffmpeg / ffprobe
                            /srv/video/data          │
                                                     └──▶ API провайдера транскрипции
                                       «video-janitor» (systemd timer, раз в час)

Внешние зависимости: Yandex OAuth, провайдер транскрипции (OpenAI-совместимый маршрут).
```

Компоненты и их единственная обязанность:

| Компонент | Обязанность |
|---|---|
| `video-api` | HTTP API, авторизация, проверка проектов, постановка заданий, forward_auth для файлов |
| `video-worker` | Выполнение заданий: анализ, прокси, рендер, транскрипция. Один процесс, две полосы |
| `video-janitor` | Почасовая очистка по срокам жизни, дамп базы по ночам |
| Caddy | TLS, лимиты тела запроса, раздача файлов с диска после forward_auth |
| SQLite | Метаданные: пользователи, сессии, токены, загрузки, ассеты, проекты, задания, рендеры, транскрипты |
| Диск `/srv/video/data` | Файлы: исходники, прокси, полоски, пики, транскрипты, рендеры. Пути выводятся из идентификаторов |

Принципы:

- Проект сохраняется целиком одним вызовом. Никаких точечных операций «добавь клип».
- Клиент никогда не задаёт путей к файлам и не передаёт аргументов ffmpeg. Команда собирается только из белого списка полей проекта.
- Каждый ресурс принадлежит одному пользователю, каждый запрос к базе фильтруется по владельцу.
- Файлы временные, база маленькая: бэкапится только база.
- Границы резов подтверждаются измеренными паузами, а не таймкодами Whisper (см. раздел 10).

## 3. Модель данных

Времена внутри медиа (точки входа и выхода, длительности, таймкоды транскрипта) в секундах с точностью до миллисекунды, хранятся как REAL. Моменты событий (`created_at`, `expires_at` и подобные) хранятся строкой ISO-8601 UTC с миллисекундами и суффиксом `Z` (`2026-09-03T10:00:00.000Z`); лексикографический порядок таких строк совпадает с хронологическим, поэтому сравнения делаются прямо в SQL. Идентификаторы: короткие случайные строки с префиксом (`usr_`, `ast_`, `prj_`, `job_`, `rnd_`, `upl_`, `tok_`).

| Таблица | Поля |
|---|---|
| `users` | id, email, name, role (`admin` / `user`), created_at, disabled |
| `sessions` | id, user_id, created_at, last_seen_at, absolute_expires_at, user_agent |
| `api_tokens` | id, user_id, name, token_hash (sha256), created_at, last_used_at, expires_at, revoked_at |
| `uploads` | id, user_id, filename, size, kind, chunk_size, path, created_at, expires_at |
| `upload_chunks` | upload_id, idx (первичный ключ из двух полей) |
| `assets` | id, user_id, kind (`video` / `audio` / `subtitle`), original_name, size, status, duration, width, height, fps, has_audio, video_codec, audio_codec, error, created_at, last_access_at |
| `projects` | id, user_id, name, version, doc (JSON, см. раздел 4), status (`draft` / `finished`), created_at, updated_at, finished_at |
| `jobs` | id, user_id, type (`analyze` / `proxy` / `render` / `transcribe`), lane (`cpu` / `net`), status (`queued` / `running` / `done` / `failed` / `canceled`), priority, target_id, params (JSON), progress (0..1), error, created_at, started_at, finished_at, worker_pid |
| `renders` | id, project_id, user_id, job_id, quality, path, size, duration, created_at, expires_at |
| `transcripts` | asset_id (первичный ключ), user_id, provider, model, language, path, stats (JSON), created_at |
| `whitelist` | email, added_by, added_at |
| `heartbeats` | name (первичный ключ), at: пульс воркера для `/healthz` |

Статусы ассета: `uploaded` → `analyzing` → `ready` → `proxy_ready`; ветка `failed`. Начиная с `ready` ассет можно ставить в проект и рендерить: звуковой анализ и полоска кадров уже есть. Видеопрокси нужен только плееру в браузере и появляется в `proxy_ready`.

`last_access_at` обновляется при сохранении проекта с этим ассетом, рендере, запросе транскрипта и при выдаче прокси через forward_auth (не чаще раза в минуту).

## 4. Формат проекта

```json
{
  "id": "prj_7f3a",
  "name": "Подкаст, выпуск 12",
  "version": 14,
  "output": { "aspect": "9:16", "fit": "pad", "fps": 30 },
  "clips": [
    { "id": "c1", "asset_id": "ast_01", "in": 12.500, "out": 48.000,
      "snap_to_pauses": true, "in_verified": true, "out_verified": false },
    { "id": "c2", "asset_id": "ast_01", "in": 95.200, "out": 130.750 }
  ],
  "music": { "asset_id": "ast_02", "volume": 0.25, "fade_in": 1.0, "fade_out": 2.0, "loop": true },
  "subtitles": { "source": "file", "asset_id": "ast_03", "mode": "burn", "style": "default" }
}
```

Поля и правила:

- `output.aspect`: `16:9`, `9:16`, `1:1`. Разрешение выводится из пропорции и качества рендера: финал с короткой стороной 1080, черновик с короткой стороной 720. `output.fit`: `pad` (поля) или `crop` (обрезка по центру). `output.fps`: 25, 30, 50 или 60.
- `clips`: от 1 до 100 элементов, порядок списка есть порядок склейки, склейка встык. `id` уникален внутри проекта. `asset_id` указывает на видеоассет владельца в статусе `ready` или выше. `0 ≤ in < out ≤ duration`, `out − in ≥ 0.1`. Один ассет может встречаться в нескольких клипах.
- `clips[].snap_to_pauses` (необязательное, по умолчанию `false`): при сохранении сервер сдвигает `in` и `out` к ближайшему краю измеренной паузы (раздел 10.6). `in_verified` / `out_verified` выставляет только сервер, присланные значения игнорируются.
- `music` (необязательное): аудио- или видеоассет владельца, `volume` 0..1, затухания ≥ 0, `loop` по умолчанию `true`.
- `subtitles` (необязательное): `source: "file"` с ассетом вида `subtitle` (SRT или VTT, время от начала готового ролика) либо `source: "transcript"` с видеоассетом, у которого есть транскрипт (сервер сам пересчитает слова через клипы). `mode`: `burn` (вжигание) или `soft` (отдельная дорожка в mp4). `style`: имя пресета, в первой версии только `default`.
- `version`: целое, растёт на 1 при каждом успешном сохранении. `PUT` с устаревшей версией получает 409 и актуальный проект в теле.
- Суммарная длительность ролика не больше 3 часов.

Сервер отвечает на сохранение полным проектом после нормализации: округление времён до миллисекунды, снэп клипов, флаги подтверждения.

## 5. API

Префикс `/api/v1`, JSON везде, кроме частей загрузки (сырые байты) и одноразовой загрузки мелких файлов (multipart). Ошибки: `{ "error": { "code": "...", "message": "...", "details": {} } }`. FastAPI отдаёт OpenAPI по `/api/v1/openapi.json`; из него агент получает описание инструментов.

| Метод и путь | Назначение |
|---|---|
| `GET /auth/login`, `GET /auth/callback`, `POST /auth/logout` | Yandex OAuth и выход |
| `GET /me` | Текущий пользователь, квота и её использование |
| `GET /tokens`, `POST /tokens`, `DELETE /tokens/{id}` | Токены для агента. Секрет показывается один раз в ответе на `POST` |
| `POST /uploads` | Создать загрузку: `{filename, size, kind?}` → `{upload_id, chunk_size, expires_at}` |
| `PUT /uploads/{id}/chunks/{n}` | Часть номер `n`, тело сырые байты |
| `GET /uploads/{id}` | `{received: [0, 1, 4], total, size}` |
| `POST /uploads/{id}/complete` | Проверка полноты, создание ассета, задание `analyze` → `{asset_id}` |
| `DELETE /uploads/{id}` | Отменить и удалить незавершённую загрузку |
| `POST /assets/upload` | Одноразовая загрузка файла до 64 МБ (SRT, музыка) |
| `GET /assets`, `GET /assets/{id}`, `DELETE /assets/{id}` | Список, карточка со ссылками на прокси, полоску, пики и метаданными, удаление |
| `POST /assets/{id}/transcribe` | `{language?}` → задание `transcribe`. Второй этап |
| `GET /assets/{id}/transcript?format=json\|srt\|vtt` | Транскрипт во времени исходника. Второй этап |
| `PUT /assets/{id}/transcript` | Загрузить свой транскрипт в нашем формате. Второй этап |
| `POST /projects`, `GET /projects`, `GET /projects/{id}` | Создать, список, получить |
| `PUT /projects/{id}` | Сохранить целиком, с `version` |
| `DELETE /projects/{id}` | Удалить проект, его задания и рендеры |
| `POST /projects/{id}/finish` | Завершить: удалить рендеры и ассеты, которые больше нигде не используются |
| `POST /projects/{id}/render` | `{quality: "draft" \| "final"}` → задание `render` |
| `GET /projects/{id}/renders` | Рендеры проекта со ссылками на скачивание и сроками |
| `GET /jobs?status=`, `GET /jobs/{id}`, `POST /jobs/{id}/cancel` | Задания и прогресс |
| `GET /renders/{id}`, `DELETE /renders/{id}` | Карточка и удаление рендера |
| `GET /files/...` | Файлы. Отдаёт Caddy после forward_auth, см. раздел 11 |
| `GET /healthz` | Здоровье: база, свободный диск, пульс воркера. Без авторизации, без подробностей |
| `GET /admin/whitelist`, `POST /admin/whitelist`, `DELETE /admin/whitelist/{email}`, `GET /admin/stats` | Только администратор |

Авторизация: cookie-сессия или `Authorization: Bearer <token>`. Все ресурсы фильтруются по владельцу, чужой идентификатор даёт 404.

Сценарий агента целиком: создать загрузку → залить части → завершить → дождаться `ready` → запустить транскрипцию → прочитать транскрипт и тишины → создать проект и сохранить список клипов с `snap_to_pauses` → рендер `draft` → проверить → рендер `final` → скачать по ссылке из карточки рендера → завершить проект.

## 6. Загрузка и хранение

### 6.1 Протокол загрузки по частям

1. `POST /uploads` с именем, размером и типом. Сервер проверяет квоту и свободный диск, создаёт запись, резервирует файл нужного размера в `/srv/video/tmp/uploads/{upload_id}`, отвечает размером части.
2. Клиент шлёт части `PUT /uploads/{id}/chunks/{n}` сырыми байтами. Сервер пишет тело потоком по смещению `n × chunk_size` (`os.pwrite`), память не растёт. Повторная отправка той же части допустима. Последняя часть может быть короче, остальные ровно `chunk_size`.
3. `GET /uploads/{id}` возвращает номера дошедших частей. Клиент досылает недостающие.
4. `POST /uploads/{id}/complete` проверяет, что дошли все части и размер файла равен заявленному, переносит файл в папку ассета одним `rename` (тот же раздел диска), создаёт ассет в статусе `uploaded` и ставит задание `analyze`.

Браузер: части уходят по три параллельно, повтор с задержкой при ошибке. Отпечаток файла (имя, размер, дата изменения) хранится в localStorage вместе с `upload_id`, после перезагрузки страницы загрузка продолжается с места разрыва. Агент реализует тот же протокол на любом языке.

Мелкие файлы (SRT, VTT, музыка до 64 МБ) идут одним `POST /assets/upload`.

Caddy: лимит тела на маршруте частей чуть больше размера части, на маршруте одноразовой загрузки 64 МБ, везде остальном 1 МБ.

| Параметр | Значение |
|---|---|
| Размер части | 32 МБ |
| Параллельных частей из браузера | 3 |
| Квота исходников на человека | 20 ГБ (настройка) |
| Отказ в новых загрузках при свободном диске меньше | 10 % |
| Незавершённая загрузка живёт | 24 часа |
| Ассет без обращений живёт | 1 день |
| Готовый рендер живёт | 1 день |

### 6.2 Расположение файлов

```
/srv/video/data/{user_id}/assets/{asset_id}/source.<ext>   исходник, наружу не отдаётся
                                            /proxy.mp4     прокси для плеера
                                            /thumbs.jpg    полоска кадров (спрайт)
                                            /thumbs.json   раскладка спрайта
                                            /peaks.json    пики звука
                                            /analysis.json паузы, порог, громкость
                                            /audio16k.wav  звук для транскрипции (удаляется после)
                                            /transcript.json
/srv/video/data/{user_id}/projects/{project_id}/renders/{render_id}.mp4
                                               /subs/{version}.srt|.vtt   производные субтитры
/srv/video/tmp/uploads/{upload_id}
```

Клиент видит только относительные ссылки вида `/files/{user_id}/assets/{asset_id}/proxy.mp4`, которые выдаёт API. Имена исходных файлов не используются в путях.

### 6.3 Очистка

Три механизма, все в `video-janitor` и в обработчиках API:

1. **Завершение проекта** (`POST /projects/{id}/finish`): удаляются рендеры проекта и те ассеты проекта, которые не входят ни в один другой незавершённый проект владельца. Запись проекта остаётся с `status = finished`, `doc` сохраняется как история.
2. **Сроки жизни** по таблице выше, проверка раз в час. Ассет с истёкшим сроком удаляется вместе с файлами; проект, ссылающийся на удалённый ассет, остаётся, но рендер по нему падает с понятной ошибкой «ассет удалён по сроку».
3. **Ручное удаление** ассета доступно всегда, кроме случая, когда он стоит в незавершённом проекте: тогда 409 со списком проектов.

Удаление файлов идёт после удаления записи, чтобы упавший процесс не оставил записи без файлов. Осиротевшие папки без записей подбирает janitor.

## 7. Анализ, полоска, пики, прокси

Задание `analyze` (полоса `cpu`, приоритет выше рендера) делает по порядку:

1. `ffprobe` в JSON: длительность, размеры, fps, кодеки, наличие звука. Файл без видеопотока становится `audio`, без обоих потоков или битый: `failed`.
2. Звук в 16 кГц моно WAV (`audio16k.wav`). Из него пики (50 значений в секунду, максимум модуля) в `peaks.json` и карта пауз двумя проходами `silencedetect` (раздел 10.4) в `analysis.json`.
3. Полоска кадров: по ключевым кадрам (`-skip_frame nokey`), приведённая к одному кадру раз в 2 секунды, не больше 600 кадров, спрайт JPEG шириной 160 px на кадр плюс раскладка в JSON. Ключевые кадры дают приблизительное время, для полоски это допустимо и на порядок дешевле полного декодирования.
4. Статус `ready`. Ставится задание `proxy`.

Задание `proxy` (полоса `cpu`, приоритет выше рендера):

| Прокси | Значение |
|---|---|
| Кодек | H.264 (`libx264`, `veryfast`, CRF 28) + AAC 96 кбит, faststart |
| Длинная сторона кадра | 640 px (было 854; снижено по замеру на VM 2026-09-04: прокси из 4K шёл 1.28× реального времени, см. `docs/benchmarks/2026-09-04-editing.md`) |
| Ключевой кадр | каждые 30 кадров (`-g 30 -keyint_min 30 -sc_threshold 0`) |

Короткий интервал ключевых кадров нужен ради точной перемотки в браузере: подрезка точек входа и выхода попадает в нужный кадр. По готовности статус `proxy_ready`.

Для `audio`-ассетов прокси это `proxy.m4a` (AAC 96 кбит); WAV наружу не отдаётся.

## 8. Превью в браузере

Браузер не склеивает видео, он имитирует склейку:

- Один элемент `video` играет текущий клип с точки входа до точки выхода, второй скрытый элемент заранее подгружает следующий клип, в момент стыка они меняются местами.
- Музыка идёт отдельным аудиоэлементом, привязанным к времени шкалы; громкость и затухания считаются на клиенте через Web Audio.
- Субтитры подключаются дорожкой WebVTT: для `source: "file"` сервер конвертирует SRT при загрузке, для `source: "transcript"` отдаёт производный VTT текущей версии проекта.
- Контейнер плеера показывает кадр в пропорции выхода с тем же режимом `pad` / `crop`, что и рендер (`object-fit: contain` / `cover`).
- Пока у ассета нет прокси, плеер показывает заглушку с кадром из полоски и прогрессом задания, шкала и звуковая волна при этом работают.

Шкала: одна дорожка, блоки клипов пропорциональны длительности, внутри кадры из полоски и волна из пиков. Перетаскивание меняет порядок, ручки по краям двигают точки входа и выхода с подсказкой времени, кнопка режет клип на два по курсору, удаление убирает блок. Неподтверждённая граница клипа с `snap_to_pauses` помечается значком. Слева панель ассетов с плеером исходника: в нём выделяется диапазон и добавляется в шкалу. Каждое изменение через 500 мс тишины уезжает на сервер сохранением проекта целиком; ответ сервера заменяет локальное состояние (снэп, флаги, версия). При 409 клиент перечитывает проект и показывает уведомление.

Фронтенд: TypeScript, Vite, без тяжёлых фреймворков; состояние проекта в одном модуле с чистыми функциями (вставка, разрез, перестановка, пересчёт времени шкалы в время исходника), которые тестируются отдельно.

## 9. Рендер

### 9.1 Воркер и очередь

Один процесс `video-worker`, две полосы:

- `cpu`: `analyze`, `proxy`, `render`. Одновременно одно задание. Порядок выбора: сначала `analyze` и `proxy`, затем `render`; внутри типа по времени постановки с чередованием пользователей, чтобы один человек не занимал воркер на час.
- `net`: `transcribe`. Одновременно одно задание, внутри до 4 параллельных запросов к провайдеру.

Задание забирается атомарным `UPDATE ... WHERE status = 'queued' ... RETURNING` (SQLite ≥ 3.35). Воркер пишет пульс в базу раз в 10 секунд; задание в `running` без пульса дольше 2 минут janitor возвращает в очередь один раз, затем помечает `failed`. Лимиты на пользователя: 1 выполняющийся рендер и не больше 2 в очереди.

### 9.2 Команда ffmpeg

Одна команда на проект, собирается чистой функцией `build_render_command(project, assets, quality) -> list[str]`, у которой нет доступа к диску: так она тестируется на фикстурах.

- Каждый клип отдельным входом: `-ss {in} -t {out − in} -i {source}`. Поиск по смещению до декодирования, поэтому полминуты из пятигигабайтной записи вырезаются быстро. Один ассет в нескольких клипах даёт несколько входов.
- Видео каждого сегмента: `fps={fps}`, затем для `pad`: `scale=W:H:force_original_aspect_ratio=decrease,pad=W:H:(ow-iw)/2:(oh-ih)/2`, для `crop`: `scale=W:H:force_original_aspect_ratio=increase,crop=W:H`; далее `setsar=1,format=yuv420p`.
- Звук каждого сегмента: `aresample=48000,aformat=sample_fmts=fltp:channel_layouts=stereo`. Клип без звука получает `anullsrc` той же длины.
- Сегменты сшиваются `concat=n=N:v=1:a=1`.
- Музыка: вход с `-stream_loop -1` при `loop`, затем `atrim=0:T`, `afade` на вход и выход, `volume`, и подмешивание к голосу `amix=inputs=2:duration=first:normalize=0`.
- Субтитры: `burn` через фильтр `subtitles=...:force_style=...` на сшитом видео, `soft` через дополнительный вход и `-c:s mov_text` с меткой языка.
- Кодирование: `libx264`, `-pix_fmt yuv420p`, AAC, `-movflags +faststart`, во временный файл с последующим переименованием в `{render_id}.mp4`.

| Качество | Короткая сторона | Пресет x264 | CRF | Звук |
|---|---|---|---|---|
| `draft` | 720 | `ultrafast` | 26 | AAC 128 кбит |
| `final` | 1080 | `veryfast` | 20 | AAC 160 кбит |

Пресеты рассчитаны на слабую VM без GPU. Замер 2026-09-04 на реальной машине (2 vCPU с долей 30 %, 4K-образец, `docs/benchmarks/2026-09-04-editing.md`): `draft` 1.36×, `final` 1.04× реального времени, пресеты оставлены; часовой финальный рендер из 4K займёт около часа, из 1080p заметно быстрее. Если рендеры станут частыми, поднимать долю vCPU до 100 % и пересчитывать замер.

### 9.3 Прогресс, отмена, ошибки

- `-progress pipe:1 -nostats`: воркер раз в секунду переводит `out_time_us` в долю от ожидаемой длительности `T = Σ(out − in)` и пишет в `jobs.progress`. Интерфейс опрашивает задание раз в 2 секунды.
- Отмена: `SIGTERM`, через 10 секунд `SIGKILL`, временный файл удаляется. Удаление проекта отменяет его задания.
- Предел времени рендера 4 часа. При ошибке в `jobs.error` уходит хвост stderr в 50 строк; распознаются типичные причины (нет звуковой дорожки, неподдерживаемый кодек, кончился диск).
- Перед запуском воркер проверяет проект заново: ассеты на месте и в статусе не ниже `ready`, свободный диск больше оценки размера результата.

### 9.4 Безопасность

Аргументы только из белого списка полей проекта, спецсимволы в фильтрах экранируются (двоеточия, запятые, кавычки в путях субтитров). Пути к файлам клиенту не показываются. Воркер живёт под `Nice=10`, `CPUQuota` и `MemoryMax` в systemd.

## 10. Транскрипция (второй этап, шов закладывается сейчас)

Опыт взят из плагина `Extensions-LLM-Chat_Pr` (клиент Cloud.ru, чанковый конвейер, спека верификации таймингов от 2026-08-06, CHANGELOG за сентябрь).

### 10.1 Провайдер

Адаптер под OpenAI-совместимый маршрут `POST {base}/v1/audio/transcriptions` (multipart: `file`, `model`, `language`, `response_format=verbose_json`, `temperature`). Первый провайдер: Cloud.ru Foundation Models, модель `openai/whisper-large-v3`. Настройки в `.env`: адрес, ключ, модель, язык по умолчанию `ru`.

Что известно о Cloud.ru Whisper и учитывается в коде:

- Пословные таймкоды не отдаёт: `timestamp_granularities[]` принимается молча, слов в ответе нет (проверено 2026-07-17 и 2026-09-02). Адаптер запрашивает слова, при ответе 400/422 с упоминанием параметра запоминает на сессию, что он не поддерживается; если слова всё же пришли, они используются.
- Границы сегментов не акустические: квантуются к целым секундам (от 8 до 62 % границ в зависимости от материала), концы в среднем на 0.35 с позже реального конца речи, бывают фантомные тайминги и выдуманные зазоры в непрерывной речи, последний сегмент вылезает за конец аудио.
- Лимит загрузки около 20 МБ на запрос, до 20 параллельных запросов. В ответе у сегментов есть `no_speech_prob`, `avg_logprob`, `compression_ratio`.
- Ошибку 413 распознавать по статусу; тело проверять только у ошибочных ответов, в успешных `verbose_json` встречаются числа вроде 23413 в токенах.

Провайдер выбирается настройкой; пословные таймкоды остаются первым критерием при выборе другого провайдера.

### 10.2 Нарезка

Из `audio16k.wav` воркер режет чанки с целью 600 секунд: граница ставится на ближайшую паузу ≥ 0.5 с в пределах ±60 с от цели, иначе жёстко. Каждый чанк кодируется в MP3 64 кбит 16 кГц моно (около 5 МБ на 10 минут), при недоступности кодека WAV. Чанки отправляются до 4 параллельно, 3 повтора с задержкой; при 413 чанк делится пополам и отправляется заново. Пустой файл чанка (меньше 1 КБ) считается ошибкой нарезки, а не пустой речью.

### 10.3 Нормализация и швы

Одна функция `normalize_chunk(result, offset)` прибавляет смещение чанка ко всем временам сегментов и слов. Второго пути нормализации нет: в плагине именно дублирующий путь однажды потерял вычитание точки входа и сдвинул весь транскрипт.

После объединения и сортировки по началу:

- **Швы чанков.** Фраза на границе приходит дважды: хвост в чанке N, голова в N+1. Сегмент, начавшийся в пределах 0.05 с от границы и накрытый хвостом предыдущего, подрезается к концу предыдущего; если после подрезки остаётся меньше 0.3 с, выбрасывается. Слова фильтруются по новому началу.
- **Клэмп к длине аудио.** Времена за пределами `[0, duration]` обрезаются; сегмент короче 0.05 с после обрезки выбрасывается.
- **Подозрительные сегменты** (`no_speech_prob > 0.5`, или `avg_logprob < −1`, или `compression_ratio > 2.4`) не удаляются, а помечаются `suspect: true`.

### 10.4 Карта пауз

Считается в задании `analyze` для всех ассетов (не только для транскрипции) двумя проходами `silencedetect` на одном пороге:

- обычный проход, минимальная пауза 0.5 с: для удаления тишин и подтверждения зазоров;
- плотный проход, минимальная пауза 0.15 с: для верификации границ и снэпа резов.

Порог не абсолютный, а «тише уровня речи на 16 дБ». Уровень речи берётся по пикам: медиана громкости самых громких 2 % окон RMS (окно 50 мс). Абсолютный порог −35 дБ в плагине не пропускал тихого гостя и считал шум громкой записи речью. Ограничения: порог не ниже −60 дБ; если пауз не нашлось и порог выше −55 дБ, повтор на 10 дБ ниже. В `analysis.json` сохраняются обе карты, использованный порог и уровень речи.

### 10.5 Верификация границ сегментов

Чистая функция `verify_segment_boundaries(segments, dense_silences)`, правило «никогда не сжимать речь»:

- начало сегмента снэпится к началу речи (концу паузы): назад до 1.0 с, вперёд до 0.25 с;
- конец сегмента снэпится к концу речи (началу паузы): вперёд до 1.0 с, назад до 0.25 с;
- граница внутри паузы получает точный ответ без ограничения окна;
- начало на нуле не трогается; конец не заходит за начало следующего сегмента; сегмент не короче 0.05 с; снэп, ломающий порядок или непересечение, откатывается.

Каждая граница получает флаг `start_verified` / `end_verified`. Граница без измеренного края речи в окне остаётся как есть с флагом `false`: «проверить нечем» честнее, чем двигать вслепую. В `stats` транскрипта: доля подтверждённых границ, число сдвинутых, максимальный сдвиг. Ориентир из плагина: целосекундные границы 61 → 29 %, медиана расстояния до края речи 0.21 → 0.09 с.

### 10.6 Резы только по паузам

Зазор между сегментами транскрипта сам по себе паузой не считается: Whisper пропускает слова, смех и перебивки. Пауза есть только там, где зазор пересекается с измеренной тишиной.

Клип с `snap_to_pauses: true` при сохранении проекта обрабатывается так: `in` ищет ближайший край паузы в окне ±0.35 с и ставится на начало речи с буфером 0.3 с внутрь паузы (не дальше её середины); `out` симметрично к концу речи. Найден край: флаг подтверждения `true`. Не найден: значение не меняется, флаг `false`, интерфейс показывает значок, агент видит флаг в ответе. Рез внутри непрерывной речи никогда не делается молча.

### 10.7 Слова

Если провайдер слов не отдал, слова внутри сегмента интерполируются равномерно по длительности сегмента и помечаются `interpolated: true` (точность около ±0.3 с). Они нужны панели транскрипта и агенту для ориентации, а не для резов: резы идут через `snap_to_pauses`. Свой транскрипт с настоящими пословными таймкодами загружается через `PUT /assets/{id}/transcript`; верификация границ и швов для него не запускается, только клэмп и проверка формата.

### 10.8 Формат транскрипта

```json
{
  "asset_id": "ast_01", "provider": "cloudru", "model": "openai/whisper-large-v3",
  "language": "ru", "duration": 3612.4,
  "segments": [
    { "id": 1, "start": 0.42, "end": 4.913, "text": "…",
      "start_verified": true, "end_verified": true, "suspect": false,
      "words": [ { "w": "Привет", "s": 0.42, "e": 0.81, "interpolated": true } ] }
  ],
  "silences": [ { "start": 4.913, "end": 5.62 } ],
  "silences_dense": [ { "start": 4.913, "end": 5.62 } ],
  "stats": { "verified_pct": 57, "adjusted": 120, "max_drift": 1.3, "seams_fixed": 4, "seams_dropped": 1 }
}
```

`GET .../transcript?format=srt|vtt` отдаёт реплики во времени исходника.

### 10.9 Субтитры из транскрипта

Для `subtitles.source: "transcript"` сервер пересчитывает слова исходника через клипы: слово с временем `t` внутри клипа `k` получает `offset_k + (t − in_k)`, слова на стыках обрезаются. Результат кэшируется как `subs/{version}.srt` и `.vtt` и пересобирается при смене версии проекта.

**Размер реплики.** Не больше двух строк, не дольше 4 с. Ширина строки зависит от кадра: около 42 знаков для 16:9, около 24 для 9:16, около 32 для 1:1 — в вертикальном кадре длинная строка либо уезжает за край, либо становится нечитаемо мелкой.

**Типографика разбиения.** Правила ниже перенесены из плагина After Effects (`Extensions-LLM-Chat/lib/pure/subtitles.js`, раздел «Subtitle typography rules»), где обкатаны на часовых подкастах. Разбиение — половина того, читаются субтитры или нет, поэтому оно описано здесь, а не оставлено на усмотрение реализации.

| | Правило |
|---|---|
| Т1 | Реплика не кончается точкой, запятой, точкой с запятой, двоеточием или тире: в субтитрах они не несут смысла и только мешают. Вопросительный, восклицательный и многоточие остаются — они меняют интонацию |
| Т2 | Реплика не начинается с точки, запятой, точки с запятой или двоеточия: Whisper оставляет их, когда фраза разорвана. Тире в начале — реплика диалога, оно остаётся |
| Т3 | Реплика не кончается предлогом, союзом или частицей, если дальше есть слова: висящее на экране одинокое «и» читатель прочитает дважды. Слово уезжает в следующую реплику, но не больше двух слов подряд |
| Т4 | Строка внутри реплики тоже не кончается ими — правило мягкое: соблюдается, когда есть годный вариант разбиения |
| Т5 | Разрыва между числом и словом, к которому оно относится, нет: «5 кг» не рвётся |
| Т6 | Разрыва после открывающей кавычки, скобки или повисшего тире нет |
| Т7 | Строки уравновешены: разброс между самой короткой и самой длинной штрафуется |
| Т8 | При равном балансе верхняя строка короче нижней — «пирамидой»: глаз читает сверху вниз и с расширяющейся строкой справляется легче |

Слово, которое уже кончается знаком препинания, считается естественным местом разрыва и под Т3 и Т4 не подпадает: «что,» в конце строки читается нормально.

**Слишком длинное слово** (не влезает в строку целиком) становится отдельной репликой: резать слово переносом хуже, чем нарушить ширину.

### 10.10 Панель транскрипта

Рядом с плеером исходника: клик по слову перематывает плеер, выделение текста создаёт клип с `snap_to_pauses: true` по границам выделенных слов. Подозрительные сегменты и неподтверждённые границы подсвечены. Это монтаж по тексту, зеркальный тому, что делает агент через API.

## 11. Вход, токены, защита

- **Вход.** Yandex OAuth (authorization code), код переносится из шлюза платформы `Brand_Image_site`. Whitelist почт в базе, управляется администратором; первый администратор задаётся в `.env`.
- **Сессии.** Серверные: в cookie (`HttpOnly`, `Secure`, `SameSite=Lax`) только случайный идентификатор. Абсолютный срок 30 дней, срок бездействия 7 дней, не больше 5 сессий на человека.
- **Токены агента.** `POST /tokens` выдаёт секрет вида `vt_<32 случайных байта>` один раз, хранится sha256. Полный доступ к ресурсам владельца, отзыв, дата последнего использования, необязательный срок. Заголовок `Authorization: Bearer`.
- **CSRF.** Для cookie-сессий изменяющие запросы проверяют `Origin` (или `Sec-Fetch-Site`) против своего домена. Токены в проверке не нуждаются.
- **Границы.** Каждый запрос фильтруется по владельцу; чужой ресурс отвечает 404. Администратор дополнительно видит whitelist и общую статистику, но не чужие проекты.
- **Раздача файлов.** Caddy: `handle /files/*` → `forward_auth` в `video-api` (`/internal/authz`, получает путь, cookie и заголовок авторизации, отвечает 200/403 после проверки, что префикс `/files/{user_id}/` совпадает с владельцем) → `file_server` с корнем `/srv/video/data`. Range-запросы и большие файлы идут мимо Python. Для рендеров Caddy добавляет `Content-Disposition: attachment`. Исходники (`source.*`) в authz всегда 403.
- **Ограничения.** Вход: 10 попыток в минуту с адреса. Загрузки: 20 новых в час на человека. Задания: 1 выполняющийся рендер и 2 в очереди на человека. Общий лимит API 600 запросов в минуту на пользователя.
- **Секреты.** `.env` с правами 0600 для сервисного пользователя: ключи Yandex, ключ провайдера транскрипции, секрет сессий, почта первого администратора. Вне git.
- **Сеть.** Входящие 22, 80, 443. Исходящие по списку: хосты Yandex OAuth, провайдер транскрипции, репозитории apt и PyPI, GitHub для деплоя.
- **Логи.** JSON в journald, идентификаторы запросов, без токенов, ключей и тел загрузок.

## 12. VM и эксплуатация

- **Машина.** Cloud.ru Evolution, Ubuntu 24.04 (ffmpeg 6.x с `libx264` и `libass` из репозитория, Python 3.12). Размер уровня машины App1..App3, без GPU. Точные цифры и пресеты рендера фиксируются после замера в первый день: скорость прокси из 4K, скорость `draft` и `final` на минутном образце.
- **Диск.** По возможности от 100 ГБ. Файлы живут сутки, квота 20 ГБ на человека, при свободном диске меньше 10 % новые загрузки отклоняются.
- **Сервисы.** `video-api.service` (uvicorn, 127.0.0.1:8010), `video-worker.service` (`Nice=10`, `CPUQuota`, `MemoryMax`), `video-janitor.timer` раз в час, Caddy с автоматическим TLS на новом поддомене. Юниты перезапускаются сами.
- **Деплой.** Репозиторий на GitHub. `deploy/deploy.sh` на VM: `git pull`, зависимости Python через `uv`, `npm ci && npm run build` для фронтенда, миграции SQLite, перезапуск юнитов. Первое развёртывание `deploy/bootstrap.sh`: пакеты, пользователь `video`, каталоги, Caddyfile, юниты, файрвол.
- **Бэкап.** `sqlite3 .backup` каждую ночь, копия вне VM (на ПК по scp или в объектное хранилище). Файлы не бэкапятся.
- **Здоровье.** `GET /healthz` (база, свободный диск, пульс воркера). Внешний пинг любым бесплатным сервисом. Шрифты для вжигания субтитров: `fonts-dejavu`, `fonts-noto`; фирменные шрифты добавляются позже.

## 13. Структура репозитория

```
server/
  app/            FastAPI: маршруты, авторизация, схемы, проверка проекта
  worker/         полосы, выбор заданий, обработчики analyze / proxy / render / transcribe
  media/          ffprobe, сборщик команд ffmpeg (чистые функции), пики, паузы, полоска
  transcription/  адаптер провайдера, нарезка, нормализация, швы, верификация, субтитры
  db/             схема SQLite, миграции
  janitor/        очистка по срокам, бэкап
web/              Vite + TypeScript: шкала, плеер, панель ассетов, панель транскрипта
deploy/           Caddyfile, systemd-юниты, bootstrap.sh, deploy.sh
tests/            pytest: unit, интеграция на синтетическом медиа, API; vitest для web
docs/superpowers/specs, docs/superpowers/plans
```

## 14. Тестирование

- **Чистая логика без медиа (pytest):** проверка и нормализация проекта, конфликт версий, сборщик команды ffmpeg (проект → список аргументов, включая экранирование), выбор задания из очереди и чередование пользователей, протокол загрузки (полнота, размер, повтор части), правила очистки, нарезка на чанки по паузам, нормализация со смещением, швы чанков, клэмп, верификация границ, снэп клипов к паузам, пересчёт субтитров через клипы, сборка реплик.
- **Интеграция на синтетическом медиа:** ffmpeg сам генерирует короткие ролики (`testsrc`, `sine`, участки тишины), тесты гонят полный путь analyze → proxy → render и проверяют длительность, размеры, наличие звука, места пауз. Идут на любой машине за секунды.
- **API:** тестовый клиент FastAPI, авторизация cookie и токеном, границы владельца, коды ошибок.
- **Фронтенд (vitest):** чистые функции модели шкалы: вставка, разрез, перестановка, пересчёт времени шкалы в время исходника и обратно.
- **Живой смоук на VM** скриптом, который проходит сценарий агента целиком через API: загрузка, проект, черновой и финальный рендер, скачивание, завершение. Прогоняется после каждого деплоя.
- **Замер производительности** отдельным скриптом на VM: прокси из 4K, `draft`, `final`, результаты в `docs/`.

## 15. Этапы (набросок для плана)

1. **M0. Скелет и вход.** Репозиторий, bootstrap VM, Caddy, Yandex OAuth, whitelist, сессии, токены, `/healthz`, замер производительности, фиксация пресетов.
2. **M1. Ассеты.** Загрузка по частям с докачкой, analyze (пики, паузы, полоска), прокси, раздача через forward_auth, квоты, janitor.
3. **M2. Проекты и шкала.** API проектов с проверкой и версиями, интерфейс шкалы и плеер, автосохранение.
4. **M3. Рендер.** Сборщик команды, воркер, прогресс, отмена, скачивание, завершение проекта, живой смоук агентским скриптом.
5. **M4. Транскрипция.** Адаптер провайдера, нарезка, швы, верификация, `snap_to_pauses`, панель транскрипта, субтитры из транскрипта, свой транскрипт.

## 16. Риски и открытые вопросы

- **Размер VM** неизвестен до замера. Если прокси из 4K идёт медленнее реального времени, готовность «сначала звук» спасает монтаж по тексту, но плеер будет ждать; тогда прокси делается на 480 px по короткой стороне или с пропуском кадров.
- **Провайдер транскрипции.** Cloud.ru не отдаёт слова; если появится провайдер с пословными таймкодами и приемлемой ценой, адаптер меняется настройкой.
- **Загрузка 5 ГБ из дома** ограничена каналом пользователя, а не VM; докачка обязана работать на практике, это первый пункт живого смоука.
- **Домен и поддомен** для нового сервиса не выбраны.
- **Шрифт субтитров:** в первой версии DejaVu / Noto, фирменный SB Sans отдельным шагом.
